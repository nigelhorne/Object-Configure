   63: =head1 SYNOPSIS
   64: 
   65: The C<Object::Configure> module is a lightweight utility designed to inject runtime parameters into other classes,
   66: primarily by layering configuration and logging support,
   67: when instatiating objects.
   68: 
   69: L<Log::Abstraction> and L<Config::Abstraction> are modules developed to solve a specific need,
   70: runtime configurability without needing to rewrite or hardcode behaviours.
   71: The goal is to allow individual modules to enable or disable features on the fly,
   72: and to do it using whatever configuration system the user prefers,
   73: and to separate run-time configuration from code.
   74: 
   75: Although the initial aim was general configurability,
   76: the primary use case that's emerged has been fine-grained logging control,
   77: more flexible and easier to manage than what you'd typically do with L<Log::Log4perl>.
   78: For example,
   79: you might want one module to log verbosely while another stays quiet,
   80: and be able to toggle that dynamically - without making invasive changes to each module.
   81: 
   82: To tie it all together,
   83: there is C<Object::Configure>.
   84: It sits on L<Log::Abstraction> and L<Config::Abstraction>,
   85: and with just a couple of extra lines in a class constructor,
   86: you can hook in this behaviour seamlessly.
   87: The intent is to keep things modular and reusable,
   88: especially across larger systems or in situations where you want user-selectable behaviour.
   89:

  114: =head3 CONFIGURATION INHERITANCE
  115: 
  116: C<Object::Configure> supports configuration inheritance, allowing child classes to inherit and override configuration settings from their parent classes.
  117: When a class is configured, the module automatically traverses the inheritance hierarchy (using C<@ISA>) and loads configuration files for each ancestor class in the chain.
  118: 
  119: Configuration files are loaded in order from the most general (base class) to the most specific (child class), with later files overriding earlier ones. For example, if C<My::Child::Class> inherits from C<My::Parent::Class>, which inherits from C<My::Base::Class>, the module will:
  120: 
  121: =over 4
  122: 
  123: =item 1. Load C<my-base-class.yml> (or .conf, .json, etc.) if it exists
  124: 
  125: =item 2. Load C<my-parent-class.yml> if it exists, overriding base settings
  126: 
  127: =item 3. Load C<my-child-class.yml>, overriding both parent and base settings
  128: 
  129: =back
  130: 
  131: The configuration files should be named using lowercase versions of the class name with C<::> replaced by hyphens (C<->).
  132: For example, C<My::Parent::Class> would use C<my-parent-class.yml>.
  133: 
  134: This allows you to define common settings in a base class configuration file and selectively override them in child class configurations, promoting DRY (Don't Repeat Yourself) principles and making it easier to manage configuration across class hierarchies.
  135: 
  136: Example:
  137: 
  138:     # File: ~/.conf/my-base-class.yml
  139:     ---
  140:     My__Base__Class:
  141:       timeout: 30
  142:       retries: 3
  143:       log_level: info
  144: 
  145:     # File: ~/.conf/my-child-class.yml
  146:     ---
  147:     My__Child__Class:
  148:       timeout: 60
  149:       # Inherits retries: 3 and log_level: info from parent
  150: 
  151:     # Result: Child class gets timeout=60, retries=3, log_level=info
  152: 
  153: Parent configuration files are optional.
  154: If a parent class's configuration file doesn't exist, the module simply skips it and continues up the inheritance chain.
  155: All discovered configuration files are tracked in the C<_config_files> array for hot reload support.
  156: 
  157: =head3 UNIVERSAL CONFIGURATION
  158: 
  159: All Perl classes implicitly inherit from C<UNIVERSAL>.
  160: C<Object::Configure> takes advantage of this to provide a mechanism for universal configuration settings
  161: that apply to all classes by default.
  162: 
  163: If you create a configuration file named C<universal.yml> (or C<universal.conf>, C<universal.json>, etc.)
  164: in your configuration directory,
  165: the settings in its C<UNIVERSAL> section will be inherited by all classes that use C<Object::Configure>,
  166: unless explicitly overridden by class-specific configuration files.
  167: 
  168: This is particularly useful for setting application-wide defaults such as logging levels,
  169: timeout values,
  170: or other common parameters that should apply across all modules.
  171: 
  172: Example C<~/.conf/universal.yml>:
  173: 
  174:     ---
  175:     UNIVERSAL:
  176:       timeout: 30
  177:       retries: 3
  178:       logger:
  179:         level: info
  180: 
  181: With this universal configuration file in place,
  182: all classes will inherit these default values.
  183: Individual classes can override any of these settings in their own configuration files:
  184: 
  185: Example C<~/.conf/my-special-class.yml>:
  186: 
  187:     ---
  188:     My__Special__Class:
  189:       timeout: 120
  190:       # Inherits retries: 3 and logger.level: info from UNIVERSAL
  191: 
  192: The universal configuration is loaded first in the inheritance chain,
  193: followed by parent class configurations,
  194: and finally the specific class configuration,
  195: with later configurations overriding earlier ones.

  197: =head2 CHANGING BEHAVIOUR AT RUN TIME
  198: 
  199: =head3 USING A CONFIGURATION FILE
  200: 
  201: To control behavior at runtime, C<Object::Configure> supports loading settings from a configuration file via L<Config::Abstraction>.
  202: 
  203: A minimal example of a config file (C<~/.conf/local.conf>) might look like:
  204: 
  205:    [My__Module]
  206:    logger.file = /var/log/mymodule.log

  208: The C<configure()> function will read this file,
  209: overlay it onto your default parameters,
  210: and initialize the logger accordingly.
  211: 
  212: If the file is not readable and no config_dirs are provided,
  213: the module will throw an error.
  214: To be clear, in this case, inheritance is not followed.

  220: =head3 USING ENVIRONMENT VARIABLES
  221: 
  222: C<Object::Configure> also supports runtime configuration via environment variables,
  223: without requiring a configuration file.
  224: 
  225: Environment variables are read automatically when you use the C<configure()> function,
  226: thanks to its integration with L<Config::Abstraction>.
  227: These variables should be prefixed with your class name, followed by a double colon.
  228: 
  229: For example, to enable syslog logging for your C<My::Module> class,
  230: you could set:
  231: 
  232:     export My__Module__logger__file=/var/log/mymodule.log
  233: 
  234: This would be equivalent to passing the following in your constructor:
  235: 
  236:      My::Module->new(logger => Log::Abstraction->new({ file => '/var/log/mymodule.log' });
  237: 
  238: All environment variables are read and merged into the default parameters under the section named after your class.
  239: This allows centralized and temporary control of settings (e.g., for production diagnostics or ad hoc testing) without modifying code or files.
  240: 
  241: Note that environment variable settings take effect regardless of whether a configuration file is used,
  242: and are applied during the call to C<configure()>.

 1689: =head1 LIMITATIONS
 1690: 
 1691: =over 4
 1692: 
 1693: =item * B<Global singleton state.> C<%_object_registry>, C<%_config_watchers>, and
 1694: C<%_config_file_stats> are package globals.  Two independent subsystems in the same
 1695: process share one hot-reload registry and one SIGUSR1 handler.  There is no
 1696: instance-level isolation.  A proper fix would wrap state in an object and allow
 1697: multiple independent C<Object::Configure> instances, but that would break the
 1698: existing constructor-call API (C<configure($class, \%params)>).
 1699: 
 1700: =item * B<Hot reload is Unix-only.> SIGUSR1 does not exist on Windows.
 1701: All signal-related paths are guarded with C<$^O ne 'MSWin32'>, so the module
 1702: loads on Windows but silently skips hot-reload registration.
 1703: 
 1704: =item * B<configure() is a God function.> At ~120 lines it handles arg validation,
 1705: config-file discovery, MRO walking, multi-file merging, env-var merging, logger
 1706: creation, and hot-reload bookkeeping.  Future versions should decompose this into
 1707: smaller, independently testable units.
 1708: 
 1709: =item * B<_deep_merge reimplements CPAN.> L<Hash::Merge::Simple> or L<Hash::Merge>
 1710: provide tested, feature-complete deep merge.  The internal C<_deep_merge> is 15
 1711: lines and correct for the current use, but does not handle arrayrefs (they are
 1712: replaced wholesale, not merged).  If array-merge semantics are ever needed, switch
 1713: to a CPAN module.
 1714: 
 1715: =item * B<No encapsulation enforcement.> Private helpers (C<_build_logger>,
 1716: C<_get_inheritance_chain>, etc.) are accessible to any caller.  L<Sub::Private>
 1717: (enforce mode) would make accidental external use a compile-time error.  It is not
 1718: added here to avoid a smoker dependency on a less-common module.
 1719: 
 1720: =item * B<configure() signature is positional, instantiate() is named.>  The two
 1721: public constructors have inconsistent calling conventions.  Normalising them to named
 1722: args would require a deprecation cycle.
 1723: 
 1724: =item * B<mro::get_linear_isa and UNIVERSAL.>  Perl's C<mro::get_linear_isa> does
 1725: not include C<UNIVERSAL> in its output unless C<UNIVERSAL> appears explicitly in
 1726: C<@ISA>.  This module appends C<UNIVERSAL> manually so that C<universal.yml> is
 1727: always discovered.  If a future Perl version changes this behaviour the guard
 1728: (C<grep { $_ eq 'UNIVERSAL' }>) remains correct.
 1729:
